# ADR-016: The legacy world bridge — view components, mission components, hosted SIM, render-driven WalkCycle

Status: accepted (Phase 5) · Date: 2026-10-15

Numbering note: ADR-002 fixed the ECS-lite shape (dataclass components in per-type dicts, phases PRE/SIM/POST/RENDER_SUBMIT, prefabs with `extends`). This ADR records how the *existing* game was brought under it without changing a frame (R1/R2), and which migrations were deliberately **not** done in Phase 5 and why.

## Context
- §6.4 migration path: adapters over legacy `Enemy`/player → `GuardRenderSystem` → NPCs/props/pickups → remove adapters last. The repository's reality: every mission owns a monolithic `game_update` that moves, collides, fights and animates through `STATE`, and the per-mission data lived as **stuffed attributes** on the shared `Enemy`, `Player` and `Door` classes (`e.m5_guard`, `d.m3_cell_door`, `v._arena_reload`; 32 `getattr(_private, default)` sites at the Phase 0 audit, ~160 mission-prefixed sites in total).
- The replay oracle hashes `Enemy`/`Player`/`Door.__dict__` (B-029). Any move of a field off those objects changes the hash *by construction*, even when behaviour is identical.
- `ae_loop`/goldens capture gameplay stills after update-only steps: anything that moves work between the update and the draw path changes pixels.

## Decision
1. **Components are views, not copies (A-010).** `game.world.legacy.LegacyRoster` mirrors `STATE.enemies / player / pickups / corpses / fire_zones / npcs / doors` into `engine.world` entities each PRE phase. The standard components (`Transform`, `Health`, `AIBrain`, `Collider`, `Faction`, `Lifetime`, `Label`, `Tags`, `LegacyRef`) are *views* onto the legacy object's own fields (`EnemyTransformView` over `rect`, `EnemyHealthView` over `hp`, …): nothing is copied, nothing moves, the legacy update keeps full authority. Identity is the Python object (`roster()._eid_of`); entities despawn when the object leaves its `STATE` list (deferred to the POST flush). The roster resets selectively when a list is rebound (B-030), never wholesale.
2. **Mission data becomes a declared component beside the mission.** `missions/mN/components.py` holds `M5Guard`, `M3Guard`, `M3Door`, `M4Guard`, `M2Role` (dataclass, slots, versioned). Call sites use one helper per family — `_m5g(e)`, `_m3g(e)`, `_m3d(d)`, `_m4g(e)`, `_m2g(e)` = `game.world.ensure(obj, Kind)` — which has exactly the `getattr(obj, "x", default)` semantics the old code relied on (defaults are the dataclass defaults; the component is created on first touch, also before the object is in any `STATE` list). Enemy type/label pairs moved to the std `Label(kind, text)` for M3/M4 (M5 keeps `M5Guard.kind/label` — it already carried them). Removed enemies are tagged `Tags({"removed"})` instead of `e._removed`. UI-owned per-sprite state (`arena_view`) lives in a UI side table (`_PoseMeta`), never on `Player`. Shared classes keep only **class-attribute defaults** for fields the legacy update genuinely writes (replay hash walks `__dict__`, so instance stuffing would have changed the hash; class attributes do not).
3. **Parity is proven twice when a field moves.** First `tools/ae_d4_replay_compat.py` re-injects every component field under its old attribute name into a copy of the hashed `__dict__` and verifies the *owner's* pre-migration baseline (150/150 for M5, M3/M4/M2, doors); only then is `baseline_v1` re-recorded (snapshot format v2 hashes components too). A plain re-record without the compat proof is the banned "silent re-baselining".
4. **The legacy update is hosted, not rewritten.** `game.world.step(fn)` runs PRE → SIM → POST; `fn` (the mission dispatcher in `core.game_core.game_update`) executes as the declared SIM system `legacy_mission_update` (order 0), so `Scheduler.describe()`/`ae_dump_components` show the true frame order and new SIM systems slot before/after it by `order`. Exceptions propagate unchanged; POST (despawn flush) still runs.
5. **`WalkCycle` stays render-driven.** The legacy sway advances in the draw path (`WalkCycle.advance(x, y)` from the mission draw code), by design: moving the advance into a SIM/POST system changes gameplay stills (phase advances during update-only captures) — a visible, non-parity change for zero gameplay value. Revisit in Phase 6 when the draw paths themselves become RENDER_SUBMIT systems (the capture harness then renders through the same queue).
6. **Not migrated in Phase 5 (documented, not hidden):** movement, collision, combat, AI decisions, interaction, pickups' effects and props' logic still run inside the mission updates. Candidate std systems `LifetimeSystem` (fire-zone `life`) and `HitFlashSystem` (`hit_flash` timers) were *not* switched on: the legacy update already decrements those fields, so a second system would double-decrement or require surgically deleting lines inside parity-protected monoliths. They become real only when a mission's update is split (Phase 6+/8), at which point the view component is replaced by an owned one and the legacy line deleted in the same change, under the replay oracle.
7. **Prefabs: kernel yes, game adoption deferred.** `engine.world.prefab` (`extends`, `diff`, `instantiate`) is implemented and unit-tested, but no mission uses it yet: today's spawn tables (`M5_ROLE_TUNING`) also set `speed`, for which there is no component, so a prefab would have split the source of truth across JSON and a Python table. Adoption is scheduled for Phase 7 (data-driven levels), when placements and role tuning move to level JSON together.

## Alternatives considered
- Copy legacy fields into real components every frame (two-way sync): rejected — double writes, ordering bugs, and the replay hash would still change.
- Rewrite `Enemy` as an entity now: rejected — strangler, not rewrite (R3); the AI monolith is ~2 k lines per mission and parity-protected only by replay/loop, not unit tests.
- Keep `getattr(e, "m5_x", default)` and merely ban new sites: rejected — D4 is an exit criterion, and the grep gate (`tools/ae_d4_gate.py`) now ratchets on *any* non-STATE receiver (hard rule for entity-like names, baseline for the rest, module calls excluded).

## Consequences
- Good: every gameplay object is an entity with declared components (dump: M5 running stage — 8 entity, 8 component types; M3 — 22 entities incl. 13 doors); D4 gate at 0; replay parity for all 5 segments via the adapters; mission data is typed and inspectable; new systems have a real scheduler to live in.
- Bad / deliberate: the adapters are an extra indirection (`ensure()` is a dict lookup per access; measured noise-level on the loop oracle, 7/7 segments identical) and must be removed last (A-010 removal plan in ADAPTERS.md). Two sandbox-vs-owner hashing caveats remain (B-024 art drift, B-029 oracle definition).
- Follow-ups: Phase 6 turns the mission draw paths into RENDER_SUBMIT systems (then revisit §5); Phase 7 adopts prefabs for guard roles; remove `A-010` only when no legacy list is the owner of an entity.
