# ADR-017: One render queue, authored order, submit-time side effects

Status: accepted (Phase 6) · Date: 2026-10-15

Numbering note: ADR-002 fixed the ECS-lite shape and phases; ADR-016 put the legacy world behind components and hosted the simulation. This ADR covers the complementary half: how a gameplay frame reaches the screen under §6.6.

## Context
- Before Phase 6 every mission painted the screen itself. In Mission 5 alone `game_draw` was a ~30-step sequence (`missions/m5/draw.py`) with two side effects hidden in the paint path (blood-decal fade/removal, `muzzle_flash_timer -= 1`), and three draw-time consumers of the shared `legacy` rng stream (rain respawns, fire-zone smoke, tram FX).
- The authored z-order in M5 is **not** y-sorted (corpses → pickups → quarter props → enemies → NPCs → Maru → player → mags), while §6.6's layer table defaults entities to a y-sort. Adopting y-sort would change pixels on overlapping actors and fail the golden oracle.
- Several legacy painters truncate coordinates at different points (`int(x - cam_x - anchor)` vs `int(x) - cam_x`), allocate scratch surfaces per frame (corpses, fire zones, water, tram smoke), and composite through special blend flags (lighting, additive fire). Any "clean" reformulation of those numbers changes pixels.

## Decision
1. **One queue, fixed layer table.** `engine.render2d.RenderQueue` implements the §6.6 layers (floor, decor_static, decals_dynamic, shadows, entities, fx_world, lighting, overlay_world, ui, debug). `core.game_core.game_draw` opens exactly one frame per gameplay draw through `game.render` (A-011); `RENDER_SUBMIT` systems then add drawables; the queue flushes to the screen. `RenderStats` (draws/blits/ms per layer, custom draws by name, UI passes, rotation-cache hits) is recorded per frame and read by `tools/ae_d6_gate.py`.
2. **Authored order wins.** Y-sort is opt-in per layer; migrants pass explicit sort keys. Inside the y-sorted entities layer M5 uses `(slot, index)` tuple keys — slots 0 corpses, 1 pickups, 2 quarter props, 3 enemies (per-enemy index from `GuardRenderSystem`), 4 HQ NPCs, 5 Maru, 6 player, 7 mags — which reproduces the legacy sequence exactly, including list order inside a slot.
3. **Truncation rule.** Primitive drawables (`RectDraw`, `EllipseDraw`, `CircleDraw`, `LineDraw`, `PolyDraw`) pass their numbers to pygame untouched, preserving each legacy call site's own float→int conversion. Submitters that truncated explicitly submit screen-space integers. `tests/unit/test_render_adapters.py` pins the twins (particles, casings, bullets, corpses, rain, fire zones, light map, prompt) pixel-for-pixel against the legacy painters.
4. **Side effects happen at submit time, never in `Drawable.draw`.** Decal fade/removal and the muzzle timer keep their legacy frame position — they run while submitting, so no other painter's view of the frame changes. The same rule covers rng: any consumer of the `legacy` stream that used to run inside a painter now runs at submit time in the authored order (tram FX step inside `decor.submit_under`, `FireZone.drawables`, `config.rain_drawables`). Reordering only the rain cost 18 k differing pixels on the quarter goldens (B-032); with all three moved together the frame is bit-identical. Render systems may consume rng only at submit, and only where the legacy painter did.
5. **Static layers are chunked bakes of the existing painters.** `StaticLayers` paints 512² chunks lazily from the untouched per-tile painter, keyed by a `(grid identity, dims, hash, quarter?)` signature with the frame-clear colour under each chunk; tiles paint strictly inside their own cell, so chunks compose exactly like per-frame blits. Rebuild happens on signature change (stage swap, level edit), never per frame.
6. **Lighting is a data-fed pass, not a mode flag.** `engine.lighting` keeps the half-res `LightBuffer` (M1–M3) and gains the multiplicative `LightMap`/`LightMapDraw` from the M5 night look: map = ambient/2 + additive falloff sprites, applied as `scene * map` then `scene + scene`, with bulb blooms after. Lamp tables stay mission data (`_STAGE_LIGHTS`, flicker kinds sampled at submit); no `LightSource` component was introduced because nothing queries light yet — the stealth readout does not exist in this tree. `lighting.sample()` is deferred until a caller exists.
7. **`UiPassDraw` is the declared UI root.** HUD, dialogue, death overlay, first-person inspect and the reticle run as named UI passes on layer 8 (§6.6's widget tree). They are counted separately from custom draws; world painting smuggled into a UI pass is still caught by the static draw-site census.
8. **Procedural character painters draw through a `Pen`.** Painters whose output *is* primitives (player avatar, weapon rigs, head adornments) take an optional pen: immediate by default (every legacy caller unchanged), recording when a mission submits through the queue. This keeps one source of geometry for the shop/Outfitter-style immediate callers and the queued gameplay path.
9. **Camera math is engine-owned; camera state is not (yet).** `clamp_top_left`, `deadzone_hold`, `ease_toward` and the max-clamp `legacy_shake` live in `engine.render2d.camera` and are called by `core.camera`; `game.render`'s `Camera2D` mirrors the legacy `(cx, cy)` every frame. Storage stays in `STATE.camera_x/y`, `screen_shake`, `cam_kick_*` (~40 readers) and the trauma model stays unused — flipping ownership is the Phase 7 ticket B-036, not a Phase 6 pixel risk.

## Consequences
- Mission 5 submits real drawables for everything: `ae_d6_gate.py --strict` reports `m5 custom=0`. The player avatar could not be baked offscreen pixel-exactly, so it goes through the `Pen` sink (decision 9, added on the owner's "continue until it's done"): `SurfacePen` replays the legacy `pygame.draw` calls verbatim, `RecordingPen` emits the same primitives as drawables; the unit pixel tests pin both paths identical for the player and all three weapon rigs.
- M1–M4 remain hosted as one whole-painter `CustomDraw` each (4 ≤ 5 allowance), each with the removal ticket B-034. The D6 gate ratchets counts **and names**, so no new legacy painter can appear unnoticed.
- New per-frame allocations are the same scratch surfaces the legacy painters already allocated (corpse layers, water sheet, fire scorch/glow); the queue itself allocates only drawable records. No budget claim is made until the owner re-runs on the reference machine.

## Alternatives considered
- Y-sorted entities per the §6.6 default: rejected for this phase — changes overlap pixels; the tuple-key scheme keeps the option open per slot.
- Baking `Player.draw` to an offscreen surface once per frame: rejected — not pixel-exact (see Consequences); tested and discarded.
- Moving draw-time mutations into POST systems: rejected — golden stills are captured after update-only steps, so anything that moves work between update and draw changes pixels (same lesson as ADR-016 §5).
- `LightSource` components + a `LightingSystem` this phase: rejected — no consumer exists in the tree; data without a query is scope creep (R8). The lamp tables are already data.
